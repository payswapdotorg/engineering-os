### Data + config (created by `postinst`, never shipped in the archive)

| Path | Created by | Semantics |
|---|---|---|
| `/var/lib/engineering-os/` | postinst | data home, owned by the system user `eos`; holds `custom.db` (SQLite) and `artifacts/` (content store, via `EOS_STORAGE_ROOT`) |
| `/var/lib/engineering-os/custom.db` | postinst | copied from the seed on **first install only**; upgrades never touch it |
| `/etc/eos/eos.env` | postinst | generated **only if absent**, `0640 root:eos`, with a randomized `NEXTAUTH_SECRET`; upgrades never touch it |

`prerm` stops + disables the service/timer; `postrm` deletes NOTHING —
`/var/lib/engineering-os` and `/etc/eos` survive remove and purge (manual
cleanup documented in `docs/07-release/installation-ubuntu.md`).

## The orphan sweep is REAL, not a filesystem sweep

`eos-orphan-sweep.timer` (daily, `Persistent=true`) →
`eos-orphan-sweep.service` (oneshot, `User=eos`) →
`/opt/engineering-os/bin/orphan-sweep.sh`, which:

1. `GET /api/status` — skips gracefully (exit 0) when the app is down;
2. skips honestly (exit 0) until `EOS_SWEEP_EMAIL`/`EOS_SWEEP_PASSWORD` are
   configured in `/etc/eos/eos.env` — the admin routes are session-gated
   (Phase-6 auth lane) and there is no API-token system;
3. otherwise signs in via the real NextAuth credentials flow
   (`csrf` → `callback/credentials`, cookie jar) with the configured
   **admin-role** service account, then calls
   `POST /api/admin/storage/scan` and
   `DELETE /api/admin/storage/orphans {"confirm":true}`.

The safety mechanism is server-side (Phase-4 semantics, see
`src/app/api/admin/storage/orphans/route.ts`): the delete re-runs a FRESH
scan inside the request and re-checks every directory against the DB right
before removal. Design note recorded for the security model: a scheduled
sweep needs an admin service account — accepted pattern, documented in
`docs/07-release/installation-ubuntu.md` and the worklog.

## Design decisions + recorded deviations

- **`Architecture: amd64`, not `all`.** The lane brief reasoned "payload is
  JS+python — no arch-specific binaries", but the payload demonstrably
  contains native linux-x64 code: the bundled Prisma client ships
  `libquery_engine-debian-openssl-3.0.x.so.node` and `sharp` ships
  `@img/sharp-linux-x64` bindings (verified in-session; both land under
  `/opt/engineering-os/node_modules`). Shipping them under `Architecture: all`
  would be a false claim on non-x64 hosts. The frozen contract's own artifact
  name (`engineering-os_<version>_amd64.deb`) matches.
- **systemd guard strengthened** in all maintscripts:
  `command -v systemctl && [ -d /run/systemd/system ]` (not just
  `command -v systemctl`). Reason: GitHub Actions runners and containers ship
  the `systemctl` binary WITHOUT a running systemd — `daemon-reload` would
  fail there and break `dpkg -i` (the CI smoke would go red for a wrong
  reason). `/run/systemd/system` exists only when systemd is actually PID 1.
- **`EOS_STORAGE_ROOT=/var/lib/engineering-os/artifacts`** is added to the
  generated env file (beyond the contract's four keys). Reason: without it the
  content store would default to `<WorkingDirectory>/data/artifacts`, i.e.
  mutable operator data under `/opt`, contradicting the documented data
  layout and the retention story. It is an already-supported variable
  (`src/lib/artifact-store.ts`, documented in `.env.example`).
- **The sweep timer is enabled by postinst** (not just the service). The
  sweep is inert-by-design until the sweep account is configured (skip + exit
  0), so enabling it is safe; operators opt out with
  `systemctl disable --now eos-orphan-sweep.timer`.
- **Unit hardening deferred.** Sandboxing directives
  (`ProtectSystem=strict`, `ProtectHome=true`, …) were considered and are
  NOT shipped: they are unverifiable in this sandbox (no root, no systemd)
  and a wrong `ReadWritePaths` set would brick the first real install.
  Recorded as follow-up work after the CI job proves the basic unit on a
  systemd host.

## Structural verification (this sandbox — no root, honest limits)

- `bash -n` on `scripts/build-deb.sh`, all three maintscripts and both
  bundled `bin/` scripts: 0 findings.
- `scripts/build-deb.sh --structure-only`: exit 0, "structure validated
  (full build runs in CI)"; emits **no** `.deb` (no fake artifacts).
- `desktop-file-validate`: **not available** in this sandbox
  (`desktop-file-utils` is not installed) — recorded; the CI packaging job
  installs it and validates `eos.desktop` for real.
- Live `dpkg -i` / `dpkg -r` and systemd unit behavior are NOT verifiable
  here (no root, no systemd). The CI `packaging` job
  (`.github/workflows/ci.yml`) is the real verification path and runs on the
  next push — install + file-layout assertions + clean removal.
